# Cosmic Transcriber Web V1.2 Critical-Change Review Gate

Status: **MANDATORY / FAIL-CLOSED**

This gate complements `tools/v12-regression-audit.mjs`.

The regression audit blocks unexplained file deletions and, as of schema v4, binds the comparison to an independently supplied expected whole-tree SHA-256 for the certified V1.1.1 materialized base. This second gate closes a different failure mode: a critical billing, checkpoint, authentication, API-key, deployment, format-binding, manifest, or dependency file could be added or modified and still be merely *reported* rather than explicitly reviewed.

It also prevents stale audit replay by binding the review to the exact complete V1.2 candidate source snapshot, not only to individually critical files.

## Required order

1. Recover and verify the exact certified V1.1.1 artifact and independently record the deterministic materialized tree SHA-256.
2. Run the exact V1.1.1 -> V1.2 regression audit with `--expected-base-tree-sha256` and write its JSON output.
3. The regression audit itself must be schema version 4 and `PASS`.
4. Its `base.provenanceVerified` must be `true`, and `base.treeSha256` must exactly equal `base.expectedTreeSha256`.
5. Run `tools/v12-critical-change-review.mjs` against that exact audit JSON and the same V1.2 candidate tree.
6. The reviewer independently recomputes the candidate whole-tree SHA-256 and file count and requires an exact match to the audit snapshot.
7. Every critical added or modified file must have an exact-hash review entry.
8. Continue to dependency-backed/runtime certification only after both provenance gates pass.

Example:

```bash
node tools/v12-regression-audit.mjs \
  --base /path/to/certified-v1.1.1 \
  --expected-base-tree-sha256 <verified-materialized-v1.1.1-tree-sha256> \
  --candidate /path/to/CosmicTranscriberWeb-1.2.0-dev \
  --json evidence/v12-regression-audit.json

node tools/v12-critical-change-review.mjs \
  --audit evidence/v12-regression-audit.json \
  --candidate /path/to/CosmicTranscriberWeb-1.2.0-dev
```

## Review file

Default path:

`docs/V1.2_CRITICAL_CHANGE_REVIEW.json`

It must be a JSON array.

For a modified critical file:

```json
{
  "path": "app.js",
  "change": "modified",
  "baseSha256": "<exact 64-hex SHA-256 from certified V1.1.1>",
  "candidateSha256": "<exact 64-hex SHA-256 from V1.2 candidate>",
  "reason": "Reviewed V1.2 change and why it preserves or intentionally changes the relevant invariant."
}
```

For an added critical file:

```json
{
  "path": "tests/format-binding.test.js",
  "change": "added",
  "candidateSha256": "<exact 64-hex SHA-256 from V1.2 candidate>",
  "reason": "New regression coverage for V1.2 client/server format binding."
}
```

`baseSha256` must be omitted or `null` for an added file.

## Critical paths

The executable gate treats these families as critical:

- `app.js`;
- Worker source;
- source paths involving session, checkpoint, transcription, billing, authentication, Access, or key handling;
- deployment/configuration/rollback/validation/certification scripts;
- tests involving session, checkpoint, billing, format, MIME, Wrangler, deployment, or authentication;
- `wrangler.toml`;
- `package.json` and `package-lock.json`;
- `RELEASE_MANIFEST.json`.

This list is intentionally conservative.

## Certified-base binding

Regression-audit schema v4 must contain all of:

- `base.version: "1.1.1"`;
- a lowercase 64-hex `base.treeSha256`;
- a lowercase 64-hex `base.expectedTreeSha256`;
- exact equality between those two hashes;
- `base.provenanceVerified:true`.

The critical-change reviewer refuses any audit without this evidence. Merely editing a saved audit to claim schema v4 while omitting or falsifying the base-provenance fields does not pass.

This executable check does not itself prove that an operator sourced the expected hash honestly. The expected hash must still come from the independently verified certified V1.1.1 artifact workflow defined in `V1.2_CERTIFIED_BASE_PROVENANCE_GATE.md`; calculating a hash from an arbitrary directory and immediately feeding it back as its own expected value is not acceptable release evidence.

## Whole-tree stale-audit protection

Regression-audit schema v4 records deterministic SHA-256 fingerprints for the complete certified-base tree and complete V1.2 candidate tree. The fingerprint includes each relative path and that file's SHA-256 in deterministic sorted order.

Before reviewing individual critical changes, `v12-critical-change-review.mjs` independently walks the current candidate tree and recomputes:

- complete candidate file count;
- complete candidate tree SHA-256.

Any added, deleted, modified, replaced, or otherwise changed tracked candidate file invalidates the previous audit, even when that file is outside the critical-path patterns. This prevents a non-critical post-audit edit from piggybacking on previously approved provenance evidence.

The audit's recorded candidate root must also exactly match the candidate directory being reviewed, preventing reuse of an audit JSON against a copied or different tree.

## Fail-closed behavior

The gate blocks when:

- the regression audit is not schema version 4;
- the regression audit status is not `PASS`;
- the audit base is not V1.1.1;
- certified-base provenance verification is absent or false;
- certified-base expected and actual whole-tree SHA-256 values are missing, malformed or unequal;
- the audit does not identify candidate version `1.2.0`;
- the audit's recorded candidate root is not the exact candidate directory currently being reviewed;
- the audit lacks a valid whole-candidate-tree SHA-256;
- the current candidate file count differs from the audited file count;
- the current whole-candidate-tree SHA-256 differs from the audited tree SHA-256;
- a critical modified file no longer hashes to the audit's recorded `candidateSha256`;
- an expected critical change lacks review evidence;
- a review hash does not exactly match the audit/current-candidate bytes;
- the review contains a stale or no-longer-critical entry;
- a review path is unsafe;
- a duplicate review entry exists;
- compared/reviewed paths rely on symbolic links or unsupported filesystem entries;
- the review JSON is malformed.

A stale entry is a blocker rather than being silently ignored. Old approvals therefore cannot become reusable waivers after source changes.

## Relationship to deletion review

Critical deletions remain governed by the stricter deletion provenance in `tools/v12-regression-audit.mjs` and `docs/V1.2_DELETION_ALLOWLIST.json`, where a deletion waiver must bind to the exact certified V1.1.1 base-file SHA-256 and contain a non-empty reason.

This critical-change gate covers **added and modified** critical files. It does not weaken or replace deletion review.

## Dependency-free tooling self-test

The CI/documentation shell can run:

```bash
node --check tools/v12-regression-audit.mjs
node --check tools/v12-critical-change-review.mjs
node --check tools/test-v12-provenance-tools.mjs
node tools/test-v12-provenance-tools.mjs
```

The self-test must preserve the real auditor's hard-pinned V1.2 lockfile provenance check; it must not introduce a test-only bypass that could also be used by release certification. Synthetic positive fixtures are used only for downstream schema-v4 critical-review behavior.

The self-test verifies, at minimum:

- omission of the expected certified-base tree SHA-256 is rejected;
- an incorrect certified-base tree SHA-256 is rejected;
- synthetic/unreviewed dependency lock is rejected after base provenance passes;
- dependency provenance failure is explicit;
- unchanged schema-v4 candidate snapshot can pass critical review with exact review hashes;
- a forged audit with certified-base provenance disabled is rejected;
- changing a non-critical file after audit is rejected by the whole-tree snapshot check;
- stale-tree rejection is explicit;
- audit replay against another candidate root is rejected;
- a non-V1.1.1 comparison base is rejected;
- a V1.2 development candidate with `releaseReady:true` is rejected.

Self-test PASS is tooling evidence only. It is not product or release certification.

## Certification meaning

A PASS from this gate means only:

> The audit carries a verified expected/actual V1.1.1 whole-tree binding, the exact complete V1.2 candidate source snapshot still matches that audit, and every critical added/modified file identified by that exact audit has an explicit reason bound to exact source hashes.

It does **not** mean V1.2 is release-ready or certified.

After it passes, the candidate must still complete all mandatory functional, static/security, mutation, secret, exact Node/npm dependency, Worker, whole-Worker integration, browser, Windows, macOS/Safari, build, fresh-ZIP, and staging acceptance gates.

`releaseReady` must remain `false` until the complete release policy is satisfied. Production V1.1.1 remains untouched during V1.2 development and staging certification.
