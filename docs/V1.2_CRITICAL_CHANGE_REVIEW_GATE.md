# Cosmic Transcriber Web V1.2 Critical-Change Review Gate

Status: **MANDATORY / FAIL-CLOSED**

This gate complements `tools/v12-regression-audit.mjs` and is part of the V1.2 release-provenance chain. It does not certify or deploy V1.2.

## Authoritative schema

The current regression-audit and critical-change-review schema is **version 5**. Any saved audit or review procedure referring to schema v4 is stale and must not be used as release evidence.

Schema v5 binds the review to the recovered all-green V1.1.1 certification evidence, the exact materialized V1.1.1 whole-tree SHA-256, the exact complete V1.2 candidate tree, and the reviewed V1.2 dependency-lock hash.

## Required order

1. Materialize the exact certified V1.1.1 source tree identified by the recovered certification evidence.
2. Independently verify its deterministic whole-tree SHA-256 against the hard-pinned certified value.
3. Run `tools/v12-regression-audit.mjs` with `--expected-base-tree-sha256` equal to that certified value.
4. Require regression-audit `schemaVersion:5` and `status:"PASS"`.
5. Require the audit's `certifiedBaseline`, `base.provenanceVerified`, expected/actual V1.1.1 tree hashes, candidate version, candidate dependency-lock hash and candidate whole-tree snapshot to match the hard-pinned/current bytes.
6. Run `tools/v12-critical-change-review.mjs` against that exact audit JSON and the same candidate directory.
7. Explicitly review every critical added, modified **or deleted** file with exact hashes and a non-empty reason.
8. Only after both provenance gates pass may dependency-backed/runtime F4 certification continue.

Example:

```bash
node tools/v12-regression-audit.mjs \
  --base /path/to/certified-v1.1.1 \
  --expected-base-tree-sha256 a67ba4aee35bf533c122f322418ac3fd4bf68601a1ae320deecb35318ffb5300 \
  --candidate /path/to/CosmicTranscriberWeb-1.2.0-dev \
  --json evidence/v12-regression-audit.json

node tools/v12-critical-change-review.mjs \
  --audit evidence/v12-regression-audit.json \
  --candidate /path/to/CosmicTranscriberWeb-1.2.0-dev
```

## Review file

Default path: `docs/V1.2_CRITICAL_CHANGE_REVIEW.json`

It must be a JSON array. Entries are exact-hash approvals, not reusable waivers.

Modified file:

```json
{
  "path": "app.js",
  "change": "modified",
  "baseSha256": "<exact certified-base file SHA-256>",
  "candidateSha256": "<exact candidate file SHA-256>",
  "reason": "Reviewed V1.2 change and why the relevant invariant is preserved or intentionally changed."
}
```

Added file: omit or set `baseSha256:null`.

Deleted file: use the exact certified-base `baseSha256`; omit or set `candidateSha256:null`. A deletion must also already be permitted by the stricter deletion provenance enforced by `tools/v12-regression-audit.mjs` and `docs/V1.2_DELETION_ALLOWLIST.json`.

## Critical paths

The executable gate intentionally treats these families conservatively:

- `app.js`;
- Worker source;
- session/checkpoint/transcription/billing/authentication/Access/key-handling source;
- deployment/configuration/rollback/validation/certification scripts;
- session/checkpoint/billing/format/MIME/Wrangler/deployment/authentication tests;
- `wrangler.toml`;
- `package.json` and `package-lock.json`;
- `RELEASE_MANIFEST.json`.

The executable scripts are authoritative for exact matching behavior.

## Fail-closed requirements

The review blocks if any of the following is true:

- audit schema is not v5 or audit status is not PASS;
- recovered V1.1.1 certification identifiers/hashes do not match the hard-pinned evidence;
- certified-base provenance verification is absent, malformed or false;
- expected and actual certified-base whole-tree SHA-256 values differ;
- candidate is not V1.2.0 or its dependency lock is not the reviewed candidate lock;
- audit candidate root, file count or whole-tree SHA-256 differs from the candidate currently being reviewed;
- a candidate file changes after the regression audit, including a nominally non-critical file;
- a critical added/modified/deleted file lacks exact review evidence;
- review hashes do not match the audited/current bytes;
- a stale/non-critical review entry remains;
- an unsafe path, duplicate entry, symbolic link or unsupported filesystem entry is encountered;
- review JSON is malformed.

This whole-tree binding prevents stale-audit replay. Any source-tree change invalidates the previous audit/review evidence and requires a new audit against the current bytes.

## Dependency-free tooling self-test

The CI/documentation shell may run:

```bash
node --check tools/v12-regression-audit.mjs
node --check tools/v12-critical-change-review.mjs
node --check tools/test-v12-provenance-tools.mjs
node tools/test-v12-provenance-tools.mjs
```

A self-test PASS proves only the release tooling behaved as tested. It is not product validation or release certification.

## Certification meaning

A PASS from this gate means only that the exact candidate snapshot is anchored to the recovered certified V1.1.1 provenance and every critical source change has an exact-hash review.

It does **not** mean V1.2 is release-ready or certified. The complete mandatory functional, static/security, mutation, secret, exact Node/npm dependency, Worker, whole-Worker integration, browser, Windows, macOS/Safari, build, package-integrity, fresh-ZIP, rollback and staging-acceptance gates must still genuinely pass.

`releaseReady` must remain `false` until the full release policy and staging acceptance are complete. Production V1.1.1 remains untouched throughout V1.2 development and staging certification.
