# Cosmic Transcriber Web V1.2 — Fast Development Mode

## Purpose

Fast Development Mode shortens the edit→feedback loop without creating a second, weaker release standard. It changes **when** expensive gates run, not **whether** mandatory gates run.

Production V1.1.1 remains untouched. V1.2 must remain `releaseReady:false` until the complete certification and staging-acceptance matrix passes.

## Core rule

Use the **smallest deterministic gate that can falsify the current change**, then escalate only when risk or subsystem boundaries require it.

Do not repeatedly run the full browser/platform/release matrix after isolated edits. Do not defer a mandatory gate past the certification/staging-candidate boundary.

## Priority order

1. Billing safety and duplicate-charge prevention.
2. BYOK/session/authentication and secret-handling boundaries.
3. Checkpoint identity, resume, cancellation and billing-ambiguity behavior.
4. Multi-format validation, MIME/extension/signature binding and upstream dispatch.
5. Worker/API integration and deployment-helper correctness.
6. User-critical browser/queue/output flows.
7. Release provenance, package integrity, rollback and staging acceptance.
8. Non-blocking polish, documentation duplication and broad refactors.

Items 1–7 may block progression. Item 8 should normally be deferred while substantive V1.2 work remains.

## Gate tiers

### Tier F0 — syntax/provenance smoke

Use for documentation, comments, isolated tooling and obviously non-runtime changes.

Typical checks:

- parser/syntax check for touched executable files;
- dependency-free provenance self-tests when provenance tooling changes;
- exact changed-file review.

F0 never certifies a runtime candidate.

### Tier F1 — focused subsystem

Default development loop for an isolated runtime change.

Run the smallest directly relevant deterministic tests, for example:

- format parser/catalog/signature tests for format changes;
- checkpoint identity tests for checkpoint changes;
- key/session tests for BYOK changes;
- deployment-helper tests for Wrangler/configuration changes.

A coherent related slice should be completed before rerunning broader suites.

### Tier F2 — critical-path regression

Required when a change touches or can affect:

- billing or paid dispatch;
- retry/ambiguity semantics;
- authentication, Access, BYOK/session encryption or key lifecycle;
- checkpoint identity/reuse/resume;
- client↔Worker format/MIME binding;
- upstream multipart filename/MIME/model mapping;
- deployment/configuration/rollback logic;
- shared code used by more than one of those subsystems.

Run focused tests plus the relevant static/security safeguards and mutation checks. Run Worker/integration tests when dependencies/runtime are available.

### Tier F3 — cross-subsystem checkpoint

Use after a substantive coherent slice or before handing a candidate to CI/staging.

Required checks include all dependency-free functional/static/mutation validation and all available Worker/integration/browser checks relevant to the changed slice.

Do not produce a release ZIP from F3.

### Tier F4 — full certification

Run only at meaningful release-candidate boundaries, after the tree is stable enough to justify the cost.

F4 contains the complete mandatory release matrix, including the reviewed exact Node/npm environment, Worker and whole-Worker integration, browser matrix, branded Chrome/Edge where required, real Safari/macOS requirements, Windows release certification, source/provenance/package-integrity checks, fresh-ZIP revalidation, aggregate all-green gate, and staging acceptance.

No lower tier can substitute for F4.

## Escalation rules

Escalate one or more tiers when:

- a focused test fails for a reason outside the edited subsystem;
- shared code crosses a trust/billing boundary;
- a change modifies serialization, metadata, routing or retry semantics used on both client and Worker;
- a dependency or lockfile changes;
- an existing hardening block is removed/replaced;
- a supposedly local change creates broad source drift;
- a staging/release candidate is being formed.

Do not rerun the complete matrix merely because a low-risk documentation or tooling edit landed.

## Repair discipline

When a gate fails:

1. inspect the first evidenced failure;
2. make the smallest coherent repair;
3. rerun the focused failing gate;
4. only then rerun the broader tier that originally exposed it.

Avoid evidence-only batch loops and unrelated refactors during repair.

## Deferred work policy

While substantive V1.2 blockers remain, defer by default:

- cosmetic UI polish that does not affect acceptance;
- duplicated prose/documentation;
- broad style-only refactors;
- speculative abstractions;
- nice-to-have tests that do not protect billing, security, correctness, compatibility or release integrity.

Deferred work must not include a mandatory acceptance criterion.

## Hard invariants

Fast mode must never:

- deploy V1.2 to production before certification/staging acceptance;
- change production V1.1.1;
- set `releaseReady:true` early;
- weaken/remove/relabel mandatory tests or safeguards;
- treat a lower-tier PASS as release certification;
- fabricate execution evidence;
- silently refresh or bless dependency provenance;
- bypass billing-ambiguity confirmation or duplicate-charge protections;
- skip exact-source/provenance checks at release boundaries.

## Current environmental blocker

The connected V1.2 branch currently contains the release-engineering shell rather than the complete `CosmicTranscriberWeb-1.2.0-dev` application source. Fast mode therefore prioritizes useful dependency-free engineering/tooling work, but must not generate product-test PASS claims until the actual source tree is available.
